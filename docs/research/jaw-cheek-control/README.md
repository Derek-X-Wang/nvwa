## 结论

建议沿用现有 Rust／Bevy 与稀疏形变路径，借鉴 MPFB／MakeHuman 对解剖部位的拆分。把**下巴尖宽度、下颌角／骨性轮廓、颧骨和脸颊饱满度**作为不同含义，不把现有 `chin_width` 放大或改名成“瘦脸”。Three.js 值得借鉴形变数据与混合契约；它不提供这些人体形状本身。Blender 值得借鉴局部形状键的创作方法。

当前不建议直接实现。**六个固定源 target 已获准获取，40,292 字节及逐文件哈希与历史清单一致；新增只读数据分析已经完成。** 建议先对一个双侧 `cheek-volume` 饱满度控制做最多六张独立源位移参考图，再决定是否值得进入 Rust。它不是纯下颌宽度，也没有证明嘴鼻保持。`chin-bones` 主要位移并非横向，暂不将其命名为 `jaw_width`。详见[数据结论与参考方案](source-data-and-reference.md)。

上一轮 [#133](https://github.com/Derek-X-Wang/nvwa/issues/133#issuecomment-6609036557) 的六张图、唯一修订和视觉 HOLD 保留。局部下巴策略未达到目标，不等于全部八参数组合都不可行。即使新增下颌控制有效，原目标中“侧前方鼻部明显变宽”的要求也仍需独立证据。

## 从现成方案借什么

| 来源 | 可借鉴的做法 | 本轮不由它证明的事情 |
| --- | --- | --- |
| Three.js | 区分相对位移与绝对坐标；多个已创作 target 按权重混合；维持顶点对应关系 | 不会从零产生下颌／脸颊形状，也不自动保嘴、拟合骨架或消除穿插 |
| MPFB／MakeHuman | 局部解剖控制分组；正负端点分别创作；对称与依赖显式表达；形状与附件／骨架重拟合分开 | 名为 `chin-bones` 不等于已经证明其作用是下颌宽度；目录存在不等于本地素材可用 |
| Blender | 稳定拓扑、共同基形、分区形状键与过渡；只为已观察到的组合／姿态缺陷做校正 | 分区工具不会自动找出正确人体区域；硬裁切影响范围也可能制造接缝 |

可复核的官方文档、固定版本代码、许可与检索限制见[开源方案调查](opensource-patterns.md)。本设计不复制 GPL 的插件实现或配置进入产品。

## 产品含义：先分清“要改哪里”

| 概念 | 当前情况／候选 | 设计决定 |
| --- | --- | --- |
| 下巴尖宽度 | 已有 `chin_width` | 旧名称、范围、默认值和输出含义保留 |
| 全头宽度 | 已有 `head_width`，影响区域广 | 不能作为局部下颌控制的同义词；保留已知鼻／嘴联动说明 |
| 下颌角／骨性轮廓 | `chin-bones` 正负对仅为待查候选 | 暂不冻结 `jaw_width` 之类产品名称；先确认实际角部、下颌边缘和过渡区运动 |
| 脸颊饱满度 | 左右 `cheek-volume` 正负对仅为待查候选 | 与颧骨宽度／前突分开；不以“饱满度”承诺纯横向缩窄 |
| 颧骨宽度／突出度 | `cheek-bones` 另属一族 | 保留为后续线索，本切片不自动扩成第三项 |

“独立控制”指有单独、准确的语义和可调自由度，不是保证所有非目标顶点完全不动。脸部曲面需要连续过渡。必须说明嘴、鼻、颈与附件可能发生的联动，并分别核对字段保留和实际画面；不能仅凭 `mouth_width` 没变就宣称嘴部几何没变。

## 推荐路径：先一个控制，再谈正式接入

### A. 恢复与检查原始输入

本阶段已完成六文件身份、非零位移、方向、单位、左右镜像以及现有 target 支持集交集的核查。所有非零位移都在 body 分组，不在 helper／joint 分组；这不证明未来骨架拟合、附件或动作正确。正负端点并非相反数。

现在可以确定源点集和数值方向，但现有分组没有唇、鼻、颈皮肤等解剖分区，不能用与 `mouth_width`／`nose_width` 支持集重叠替代实际解剖或看图结论。尚不设嘴部视觉容差。若实际效果只改变下巴尖、主要影响额头／全头，或来源不能匹配，就保留拒绝记录并停止该候选，不按文件名强行准入。

### B. 原工具的最小语义对照

这是下一轮可选择的有界实验，**本轮不执行**：先选择双侧脸颊饱满度，一个共同中性基线与 `[-1,0,+1]` 三个合法状态，固定正面／35° 视图，最多六张参考图。已检查的路径没有可用 MPFB addon；全局安装状态仍未知。建议用已有 Blender 做独立源位移参考，明确不称其为 MPFB 原生操作等价证明。先证明形状确实变化在所需部位，再花成本改 Rust。

看图问题只有三个：轮廓是否明显改变在正确部位；嘴／鼻／颈和可见附件是否出现新增不合意变化；从中性形状出发的正负端点是否符合命名。若参考工具内也没有所需形状，停止，不开始 Rust 拟合、追加采集或通用求解器。

### C. 原工具证明有收益后，才冻结 Rust 实现范围

复用现有稀疏位移、拟合、蒙皮与预览路径，不引入 Three.js、另一渲染器、任意 target 导入器或宏参数系统。下列是必须设计的兼容点，不是已经批准的修改：

- **旧身份不变。** 现有八参数 profile、base manifest、Work 和外观绑定保留原字节与意义；不在旧 profile 中静默增加参数或改变旧值。沿用[版本化后端规则](../../adr/0007-versioned-character-backends.md)，新能力采用明确的新 profile／素材身份。当前精确 canonical dispatch 要求新参数目录使用新的显式 backend 版本，具体编号在最终实施范围中冻结；不预设改变 Work schema4。
- **命令继续共享。** `set_parameters`、事务、撤销／重做和保存语义复用。新增控制的零值应保留基线；从旧 Work 进入新能力必须显式选择。CLI／界面创建入口不能悄悄改变旧输出。
- **左右组合显式。** 当前绑定是一负一正两个叶文件。对称脸颊需要左右各一套端点；“左右作为显式叶组”与“生成有完整来源记录的对称复合对”是两种方案，前者减少派生素材但改动绑定，后者减少运行时机制却增加素材生成责任。实际源数据确认左右文件在反射下精确匹配，但当前阶段仍不选择生产映射方案；未来两侧应按官方对称规则各用完整权重，不能取平均或只用单侧代替。
- **附件重新验证。** 新 base 需要明确的外观兼容绑定，不能借用旧 base 的哈希。复用皮肤／眼睛／头发原载荷不等于拟合已经通过；旧动作也须另验。
- **准入成本单列。** Core 的有限目录、运行时目标加载、素材验证、外观绑定、CLI／界面创建与既有原始来源校验均受影响。当前冻结门禁已有六份完整上下文；保留旧清单、样本和断言。实施前列出必要精确新准入及耗时影响，不在此设计中同意扩验证框架、测试矩阵或 CI 预算。

主要成本不在新增滑条，而在实际素材语义、附件／骨架兼容和旧作品身份保留。当前只能给出条件性范围，不能承诺完整接入的文件数、耗时或一次成功。

## 最小验收与停止线

前面的六张参考图只回答“素材是否适合”，不能替代生产验收。只有参考阶段通过，才为一个新控制冻结：

1. 原始来源／单位／顶点对应，零值、端点及少量组合的独立检查；不自动铺开所有旧参数的笛卡尔积。
2. 同一输入在参考工具与实际 Rust 路径中的形状含义一致；真实固定视角看图，独立审查先看画面再看参数。
3. 一次真实 AI 使用：发现准确的控制含义，按目标创作并看图；最多一次修订，其他设置和旧 Work 保留。
4. CLI 校验／保存重载、普通 Web Open／Save 交换、相关已有动作和现有完整自动测试／native／Wasm／CI 门禁；普通桌面 UI 按仓库策略延后。

素材缺失、语义不符、需要第三族、明显嘴部／附件问题、需要重做 rig／大幅运行时、源码准入或预算扩大时，记录并停止该切片。校正 target 只针对实际出现且获准处理的缺陷；不先造通用校正框架。
