# Native command-key and clipboard observation

This is a bounded dependency-source investigation, not an established physical-keyboard defect. Actual native pointer focus, triple-click selection, ASCII `typeText`, Open recovery and playback succeeded on the repaired PR17 binary. CUA `App.pressKey("super+a")`, including a 200 ms hold, did not select the field. `App.paste` did not replace its contents. `typeText` then inserted a sentinel into the existing text; triple-click plus `typeText` replaced it successfully. These attempted adapter operations are **unverified for human Command/clipboard behavior**, not NOT-RUN attempts or a proven product crash. No clipboard-provider error was found in the application log.

Independent GPT-6.1 Sol source inspection identified these hypotheses:

1. Installed bevy_egui 0.42.0 `src/input.rs:375` processes the full keyboard batch into final modifier state, before `src/input.rs:684,726–730` stamps that state onto keys. A complete modifier-down/key-down/key-up/modifier-up batch can therefore lose the modifier. Egui select-all requires command (`egui 0.36.2 src/text_selection/cursor_range.rs:116`). A supported CUA held chord does not establish the event ordering.
2. Installed winit 0.30.13 macOS `src/platform_impl/macos/view.rs:929` emits separate modifier key events only for recognized nonzero flagsChanged keycodes. Ordinary key-event flags can produce `ModifiersChanged` (`:477,1046`), which bevy_winit 0.19.1 `src/state.rs:264–427` does not explicitly consume. Synthetic mapping may differ from a physical modifier key.
3. Native paste depends first on recognized Command+V (`bevy_egui src/input.rs:745`). Clipboard support is enabled in root Cargo.toml, and arboard initialization/read failures would log errors (`bevy_egui src/lib.rs:1478,1530`). Clipboard-provider failure alone would not explain select-all.

Next discriminating physical tests: hold Command before A and briefly afterward; compare a quick chord and held chord. Then paste only a task-owned sentinel, checking the exact application log. If physical input works but all supported adapter chords fail, investigate adapter mapping rather than changing product key contracts. Exact event instrumentation has not run. No private clipboard contents or credential stores were inspected.

IME defaults and preedit/commit forwarding exist in the installed integration; this does not verify real composition. The final font build also rendered a loaded Unicode filename and saved/reopened its real path. Native CUA bulk `typeText` omitted the Chinese characters while preserving ASCII delimiters. The first native CUA slider drag produced no edit; the next attempt was blocked when macOS locked. After the user manually unlocked it, full-pixel and half-coordinate drag attempts again produced no edit; actual full-pixel track click edited the parameter and native Undo/Redo/persistence passed. Per-key Space focus protection and actual window zoom/recovery also passed. See [unlocked acceptance](UNLOCKED-ACCEPTANCE.md). Physical Chinese IME, physical clipboard/modifier keys, native continuous drag and OS-level blur/refocus remain separate acceptance cases under issue #2. No unlock bypass was attempted.
